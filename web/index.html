03 De dónde salen ingesta.yml · lunes

Tres fuentes públicas, un lunes a la semana.

GitHub Actions baja las tres cada lunes y las commitea en un repo de datos, con la URL de origen y el sha256 de cada archivo en un manifiesto. La zona raw vive fuera de Fabric a propósito: la capacidad es desechable y el histórico no (decisión #1).

04 Cómo corre solo 3 horarios · 0 clics

Tres horarios a la semana, y nadie le da a «Run».

El lunes se baja lo nuevo, el martes se procesa y el domingo se da mantenimiento. Cada capa espera a que la anterior salga en verde: si una truena, las de adelante no corren sobre datos a medias. No hay tabla de corridas hecha a mano; el registro es el monitoring hub de Fabric, y el aviso de falla es el suyo (decisión #31).

1 lunes 06:00 · GitHub Actions

ingesta.yml

  1. profecouna sonda de metadatos decide si vale la pena bajar el bundle
  2. conasami · inpcse bajan siempre y se escriben sólo si cambió el sha256
  3. commiten indice-gansito-datos, con su manifiesto

Lo normal es no encontrar nada: Profeco publica una vez al mes, sin día fijo.

2 martes 03:00 · Fabric prod

pl_master

  1. pl_bronzenb_10 → nb_11 → nb_12, en serie y en una sola sesión de Spark
  2. Wait 120 s
  3. pl_silvernb_20 → nb_21 → nb_22, igual
  4. Wait 120 s
  5. pl_goldnb_30 → refresh de sm_gansito → nb_50_export

La espera es fija a propósito: la sesión de la capa anterior tarda hasta dos minutos en soltar la capacidad (decisión #41).

3 domingo 03:00 · Fabric prod

pl_mantenimiento

  1. OPTIMIZEcompacta los archivos chicos que dejan los MERGE
  2. VACUUMborra los archivos que ya nadie referencia y tienen más de siete días
  3. refreshel modelo vuelve a apuntar a la versión nueva
  4. re-clonel bronze de dev se copia de prod

El orden importa: un VACUUM antes del refresh deja al reporte leyendo archivos que ya no existen (decisión #33).
